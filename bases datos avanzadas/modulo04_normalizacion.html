01. Contexto Empresarial & El Problema en Producción

La trampa de la 'tabla plana' desnormalizada y el costo catastrófico de las anomalías operativas

En etapas tempranas de desarrollo, es común que aplicaciones o planillas de cálculo consoliden múltiples conceptos de negocio en una única tabla plana o sábana desnormalizada (UNF — Unnormalized Form). Bajo una apariencia engañosa de simplicidad, esta estructura engendra una degradación sistemática de la integridad referencial y causa fallas operativas severas.

Esquema Desnormalizado en UNF (Tabla Plana Sucia)

Una sola tabla almacena matrículas, estudiantes, cursos, facultades y decanos: 

-- ⚠️ Tabla con listas no atómicas y dependencias mezcladas:
CREATE TABLE matriculas_unf (
    estudiante_id   INT,
    nombre          VARCHAR,
    ciudad          VARCHAR,
    cursos_lista    VARCHAR, -- 'SQL Avanzado, Python AI'
    carrera         VARCHAR,
    facultad        VARCHAR,
    decano          VARCHAR
);

❌ Consecuencia: No se puede registrar una nueva carrera sin matricular al menos a un estudiante, y actualizar el decano requiere modificar miles de filas redundantes.

Esquema Normalizado en 3FN / BCNF

Desacoplamiento formal en entidades independientes con claves primarias y foráneas: 

-- ✅ Separación de responsabilidades relacionales:
CREATE TABLE facultades   (facultad_id INT PK, decano VARCHAR);
CREATE TABLE carreras     (carrera_id INT PK, fac_id INT FK);
CREATE TABLE estudiantes  (estudiante_id INT PK, carrera_id INT FK);
CREATE TABLE inscripciones(estudiante_id INT FK, curso_id INT FK,
                           PRIMARY KEY(estudiante_id, curso_id));

✅ Resultado en Producción: Cada hecho se registra en exactamente un solo lugar. Integridad garantizada y costos de actualización constantes $O(1)$.

Las 3 Anomalías Catastróficas de los Esquemas No Normalizados

Tipo de Anomalía Manifestación Operativa Impacto Crítico en Producción & Solución Relacional
Anomalía de Inserción Imposibilidad de registrar una entidad de negocio válida sin asociarle obligatoriamente datos secundarios inexistentes. No se puede dar de alta la carrera 'Inteligencia Artificial' si aún no tiene alumnos matriculados, porque la clave primaria compuesta rechaza nulos. Solución: Aislar la entidad carreras en su propia tabla con clave primaria propia.
Anomalía de Actualización La modificación de un dato atómico exige actualizar cientos o miles de tuplas repetidas a lo largo de la base de datos. Si el decano cambia de apellido, una consulta UPDATE que falle a mitad del proceso deja la base de datos con dos decanos diferentes para la misma facultad (inconsistencia de lectura). Solución: Guardar el decano una única vez en la tabla facultades.
Anomalía de Borrado La eliminación de un registro transaccional arrastra silenciosamente la existencia de información maestra de la organización. Si el único estudiante matriculado en 'Redes & Cloud' se retira y se borra su fila, se borra de la existencia el registro de la carrera y su facultad. Solución: Mantener tablas maestras independientes de las tablas de relación transaccional.

02. Cimiento Teórico Formal: Dependencias Funcionales & Axiomas de Armstrong

La formalización matemática de Edgar F. Codd y William W. Armstrong para la descomposición relacional

La normalización no es un criterio estético subjetivo, sino una disciplina matemática rigurosa fundamentada en la teoría de **Dependencias Funcionales** sobre el Álgebra Relacional:

Definición Formal de Dependencia Funcional (FD)

Sea una relación $R$ con un conjunto de atributos $U$. Se dice que un conjunto de atributos $Y \subseteq U$ tiene una Dependencia Funcional respecto a $X \subseteq U$ (denotado como $X \rightarrow Y$) si y solo si para cada par de tuplas $t_1, t_2 \in R$:

$$\forall t_1, t_2 \in R, \quad \big(t_1[X] = t_2[X]\big) \implies \big(t_1[Y] = t_2[Y]\big)$$

Interpretación: El valor de $X$ determina unívocamente el valor de $Y$. Si dos filas coinciden en $X$, están obligadas matemáticamente a coincidir en $Y$.

Los 3 Axiomas Fundamentales de Armstrong

En 1974, William W. Armstrong demostró que cualquier conjunto de dependencias funcionales verdaderas puede derivarse mediante un sistema formal deductivo **sólido y completo**:

1. Reflexividad

Si $Y \subseteq X$, entonces se cumple trivialmente que:

$$X \rightarrow Y$$

Ejemplo: (id_estudiante, carrera) -> id_estudiante.

2. Aumento

Si $X \rightarrow Y$ y se agrega un atributo arbitrario $Z$, entonces:

$$XZ \rightarrow YZ$$

La determinación funcional se preserva al expandir el contexto.

3. Transitividad

Si $X \rightarrow Y$ y simultáneamente $Y \rightarrow Z$, entonces:

$$X \rightarrow Z$$

Es la causa raíz que la 3FN se encarga de aislar y resolver.

Escalera de las 6 Formas Normales (1FN a 5FN & BCNF)

Forma Normal Condición Teórica Necesaria Problema / Dependencia que Elimina Mecanismo de Descomposición
1FN Todos los dominios contienen únicamente valores atómicos; sin grupos repetitivos. Listas multivaluadas en una sola celda (ej. 'SQL, Python') y columnas duplicadas (tel_1, tel_2). Desglose de listas en múltiples filas con clave compuesta unívoca.
2FN Está en 1FN y ningún atributo no clave depende de un subconjunto propio de la clave primaria. Dependencias Parciales: Atributos que solo dependen de una parte de la clave compuesta. Separación de la entidad principal de las entidades de detalle 1:N.
3FN Está en 2FN y ningún atributo no clave depende transitivamente de la clave primaria. Dependencias Transitivas ($X \rightarrow Y \rightarrow Z$): Datos de terceros embebidos en la tabla. Extracción de atributos intermedios a una tabla catálogo independiente con FK.
BCNF Para toda dependencia funcional $X \rightarrow Y$ no trivial, $X$ debe ser estrictamente una Superclave. Anomalías sutiles cuando existen múltiples claves candidatas compuestas superpuestas. Descomposición de determinantes que no son superclaves en tablas separadas.
4FN Está en BCNF y no existen Dependencias Multivaluadas Independientes ($X \twoheadrightarrow Y$). Explosión combinatoria (producto cartesiano espurio) entre colecciones ortogonales (ej. Habilidades e Idiomas). Bifurcación en 2 tablas binarias independientes asociadas a la entidad padre.
5FN (PJNF) Toda Dependencia de Unión ($JD(*(R_1, ..., R_n))$) está implícita por las claves candidatas. Restricciones cíclicas en relaciones ternarias (o n-arias) que generan tuplas fantasma al reconstruirse. Descomposición en $N$ proyecciones simétricas con reconstrucción sin pérdidas (*Lossless Join*).

03. Glosario de Palabras Clave

Conceptos formales, definiciones matemáticas y sintaxis DDL para normalización relacional

DEPENDENCIA FUNCIONAL (X -> Y) Fundamento Matemático
DEFINICIÓN FORMAL:
X -> Y  <=>  Para todo par de tuplas (t1, t2), si t1[X] = t2[X] entonces t1[Y] = t2[Y].
Donde X es el 'Determinante' e Y es el 'Dependiente'.
EJEMPLO EN SQL:
-- El documento de identidad determina unívocamente el nombre del cliente:
-- cedula_id -> (nombre, fecha_nacimiento, ciudad_residencia)
CREATE TABLE clientes (
    cedula_id INT PRIMARY KEY,
    nombre VARCHAR NOT NULL,
    ciudad_residencia VARCHAR NOT NULL
);
  • Determinante: El conjunto de atributos a la izquierda de la flecha que fija sin ambigüedad el valor del dependiente.
  • Dependencia Trivial: Ocurre cuando el dependiente ya forma parte del determinante ($X \rightarrow Y$ con $Y \subseteq X$). No aporta restricciones semánticas nuevas.
  • Cierre de Atributos ($X^+$): El conjunto total de atributos funcionalmente determinados por $X$ bajo los axiomas de Armstrong. Si $X^+ = U$ (todo el universo de columnas), entonces $X$ es una Superclave.
PRIMERA FORMA NORMAL (1FN - ATOMICIDAD) Regla de Dominio
DEFINICIÓN FORMAL:
Una relación R está en 1FN si y solo si todos los atributos subyacentes contienen valores atómicos
e indivisibles pertenecientes a un dominio simple. Se prohíben arreglos, tuplas o conjuntos en una celda.
EJEMPLO EN SQL:
-- ❌ INCORRECTO (Viola 1FN por celda con múltiples valores):
-- INSERT INTO estudiantes VALUES (101, 'Carlos Mendoza', 'SQL, Python, Cloud');

-- ✅ CORRECTO EN 1FN (Cada fila representa un único hecho atómico):
CREATE TABLE estudiante_cursos_1fn (
    estudiante_id INT,
    curso_nombre VARCHAR,
    PRIMARY KEY (estudiante_id, curso_nombre)
);
  • Atomicidad Relacional: Cada intersección fila-columna almacena un único valor escalar indivisible según la semántica del dominio.
  • Eliminación de Grupos Repetitivos: Prohíbe matrices horizontales artificiales (telefono_1, telefono_2, telefono_3).
  • Efecto Colateral Didáctico: Al pasar de listas a filas atómicas con clave compuesta, se duplican los atributos descriptivos del estudiante en múltiples filas, dando origen a la necesidad de la 2FN.
SEGUNDA FORMA NORMAL (2FN - DEPENDENCIA COMPLETA) Regla de Clave Compuesta
DEFINICIÓN FORMAL:
Una relación R está en 2FN si está en 1FN y ningún atributo no primo (que no forma parte de ninguna clave)
depende funcionalmente de un subconjunto propio de cualquier clave candidata.
EJEMPLO EN SQL:
-- Descomposición de la clave compuesta (estudiante_id, curso_id):
-- El nombre del estudiante solo depende de estudiante_id (dependencia parcial).

-- 1. Tabla de la Entidad Maestra:
CREATE TABLE estudiantes (estudiante_id INT PRIMARY KEY, nombre VARCHAR);

-- 2. Tabla de la Relación Muchos a Muchos:
CREATE TABLE inscripciones (
    estudiante_id INT REFERENCES estudiantes(estudiante_id),
    curso_id INT REFERENCES cursos(curso_id),
    fecha_inscripcion DATE NOT NULL,
    PRIMARY KEY (estudiante_id, curso_id)
);
  • Aplicabilidad: Si la clave primaria de una tabla es simple (un solo atributo escalar), la tabla está automáticamente en 2FN una vez alcanzada la 1FN.
  • Dependencia Funcional Parcial: Ocurre cuando un atributo $A$ depende solo de una parte de la clave compuesta ($X_1 \subset X$ tal que $X_1 \rightarrow A$).
  • Solución Estructural: Los atributos parciales se trasladan a una nueva tabla donde su determinante es la clave primaria completa.
TERCERA FORMA NORMAL (3FN - NO TRANSITIVIDAD) Regla de Desacoplamiento
DEFINICIÓN FORMAL:
Una relación R está en 3FN si está en 2FN y ningún atributo no primo depende transitivamente
de la clave primaria: X -> Y -> Z (donde Y no es superclave ni clave candidata).
EJEMPLO EN SQL:
-- En estudiantes: estudiante_id -> carrera_id -> nombre_carrera (Transitiva)
-- Separamos la carrera en su propia relación:

CREATE TABLE carreras (
    carrera_id INT PRIMARY KEY,
    nombre_carrera VARCHAR NOT NULL
);

CREATE TABLE estudiantes (
    estudiante_id INT PRIMARY KEY,
    nombre VARCHAR NOT NULL,
    carrera_id INT REFERENCES carreras(carrera_id)
);
  • El Lema Clásico: "Todo atributo debe depender de la clave, de toda la clave, y de nada más que de la clave (con la ayuda de Codd)".
  • Eliminación de Redundancia: Impide que si 500 estudiantes pertenecen a la carrera 'Ing. Sistemas', el nombre de la carrera se almacene 500 veces.
  • Preservación de Dependencias: La 3FN garantiza siempre una descomposición sin pérdidas (*Lossless*) que a la vez preserva todas las dependencias funcionales originales.
FORMA NORMAL DE BOYCE-CODD (BCNF) Superclave Estricta
DEFINICIÓN FORMAL:
Una relación R está en BCNF si y solo si para cada Dependencia Funcional no trivial X -> Y,
el determinante X es estrictamente una SUPERCLAVE de R.
EJEMPLO EN SQL:
-- Si en asesorias(estudiante_id, materia, profesor):
-- profesor -> materia, pero 'profesor' NO es superclave de la tabla completa.
-- BCNF exige descomponer en:
CREATE TABLE profesor_materia (
    profesor_id INT PRIMARY KEY,
    materia_id INT NOT NULL
);
CREATE TABLE estudiante_profesor (
    estudiante_id INT,
    profesor_id INT REFERENCES profesor_materia(profesor_id),
    PRIMARY KEY (estudiante_id, profesor_id)
);
  • Superación de la 3FN: Toda relación en BCNF está automáticamente en 3FN, pero no toda relación en 3FN cumple BCNF (ocurre cuando hay claves candidatas compuestas superpuestas).
  • Compromiso Teórico: En raros casos, transformar un esquema a BCNF puede perder la capacidad de verificar ciertas dependencias funcionales mediante simples restricciones de clave foránea.
4FN & 5FN (MULTIVALUADOS & UNION DE PROYECCIONES) Fagin & PJNF
DEFINICIÓN FORMAL:
4FN: Elimina Dependencias Multivaluadas Independientes (MVD: X ->> Y).
5FN (PJNF): Asegura que la tabla no puede descomponerse en proyecciones más pequeñas
que generen tuplas espurias al reconstruirse mediante JOINs naturales: * (R1, R2, ..., Rn).
EJEMPLO EN SQL:
-- 4FN: Separar Habilidades e Idiomas del Estudiante para evitar Producto Cartesiano:
CREATE TABLE estudiante_habilidades (estudiante_id INT, habilidad VARCHAR, PRIMARY KEY(estudiante_id, habilidad));
CREATE TABLE estudiante_idiomas     (estudiante_id INT, idioma VARCHAR, PRIMARY KEY(estudiante_id, idioma));

-- 5FN: Descomposición ternaria cíclica simétrica (Vendedor, Cliente, Marca):
CREATE TABLE vendedor_marcas   (vendedor_id INT, marca VARCHAR, PRIMARY KEY(vendedor_id, marca));
CREATE TABLE cliente_marcas    (cliente_id INT, marca VARCHAR, PRIMARY KEY(cliente_id, marca));
CREATE TABLE vendedor_clientes (vendedor_id INT, cliente_id INT, PRIMARY KEY(vendedor_id, cliente_id));
  • Explosión Combinatoria: Si un empleado tiene 4 habilidades y habla 3 idiomas, guardarlos juntos en una tabla 3FN genera $4 \times 3 = 12$ tuplas artificiales sin semántica real.
  • Tuplas Espurias (Filas Fantasma): Datos que aparecen como resultado de un JOIN que no existían en el mundo real, causados por dependencias de unión no controladas.

04. Laboratorio SQL DDL & Desglose Línea a Línea

Implementación ejecutable en DuckDB de la refactorización desde tabla plana a esquema normalizado

A continuación se presenta el script corporativo completo de refactorización relacional. Observa cómo mediante INSERT INTO ... SELECT DISTINCT migramos una tabla sucia de matrículas a un esquema formal desacoplado en 3FN: 

-- 1. Tabla Maestra de Facultades (Elimina dependencia transitiva del decano)
CREATE TABLE facultades_3fn (
    facultad_id      INT PRIMARY KEY,
    facultad_nombre  VARCHAR NOT NULL,
    decano_facultad  VARCHAR NOT NULL
);

-- 2. Tabla de Carreras Universitarias (Relacionada 1:N con Facultades)
CREATE TABLE carreras_3fn (
    carrera_id       INT PRIMARY KEY,
    carrera_nombre   VARCHAR NOT NULL,
    facultad_id      INT NOT NULL REFERENCES facultades_3fn(facultad_id)
);

-- 3. Tabla Maestra de Estudiantes (Relacionada 1:N con Carreras)
CREATE TABLE estudiantes_3fn (
    estudiante_id    INT PRIMARY KEY,
    nombre           VARCHAR NOT NULL,
    ciudad           VARCHAR NOT NULL,
    carrera_id       INT NOT NULL REFERENCES carreras_3fn(carrera_id)
);

-- 4. Tabla de Catálogo de Asignaturas (Atómica)
CREATE TABLE cursos_3fn (
    curso_id         INT PRIMARY KEY,
    curso_nombre     VARCHAR NOT NULL UNIQUE,
    creditos         INT CHECK (creditos > 0)
);

-- 5. Tabla de Relación N:M de Inscripciones (Clave Compuesta en 2FN/3FN)
CREATE TABLE inscripciones_3fn (
    estudiante_id    INT REFERENCES estudiantes_3fn(estudiante_id) ON DELETE CASCADE,
    curso_id         INT REFERENCES cursos_3fn(curso_id) ON DELETE RESTRICT,
    fecha_matricula  DATE NOT NULL,
    PRIMARY KEY (estudiante_id, curso_id)
);

-- 6. Migración Segura de Datos Limpios sin Duplicación:
INSERT INTO facultades_3fn VALUES (1, 'Facultad de Ingeniería', 'Dr. Roberto Gómez');
INSERT INTO carreras_3fn   VALUES (10, 'Ingeniería de Sistemas', 1), (20, 'Redes & Cloud', 1);
INSERT INTO estudiantes_3fn VALUES 
(101, 'Carlos Mendoza', 'Bogotá', 10),
(102, 'Ana María Gómez', 'Medellín', 10),
(103, 'Luis Fernando Torres', 'Cali', 20);

Desglose Anatómico de las Cláusulas DDL

Línea DDL Cláusula / Restricción Mecánica de Integridad en el Motor Relacional
L1 - L5 facultad_id INT PRIMARY KEY Define la entidad independiente de facultades. El decano se vincula exclusivamente a esta entidad, impidiendo anomalías de actualización.
L7 - L11 REFERENCES facultades_3fn(facultad_id) Establece la clave foránea que preserva la integridad referencial. Una carrera no puede existir huérfana de facultad.
L13 - L18 carrera_id INT REFERENCES carreras_3fn Elimina la dependencia transitiva: el estudiante se vincula a su carrera ($E \rightarrow C$), y la carrera a su facultad ($C \rightarrow F$).
L20 - L24 curso_nombre VARCHAR UNIQUE Asegura atomicidad y unicidad del nombre del curso en el catálogo, impidiendo duplicados en el diccionario.
L26 - L32 PRIMARY KEY (estudiante_id, curso_id) Define la clave primaria compuesta de la relación N:M, garantizando que un estudiante no pueda inscribir dos veces la misma asignatura en la misma matrícula.
L27 - L28 ON DELETE CASCADE / RESTRICT Reglas semánticas de integridad: si se borra un estudiante se eliminan sus inscripciones (`CASCADE`), pero no se puede borrar un curso si tiene alumnos matriculados (`RESTRICT`).

07. Anti-Patrones de Normalización & Consideraciones de Producción

Errores arquitectónicos comunes: desde la sobre-normalización hasta el abuso de columnas de texto

Anti-Patrón 1: Grupos Repetitivos en Columnas Horizontales (Violación Flagrante de 1FN)

Crear columnas numeradas secuencialmente como telefono_1, telefono_2, telefono_3 o curso_1, curso_2 limita artificialmente la cantidad de registros por entidad, desperdicia almacenamiento con campos nulos y hace imposible indexar o consultar mediante filtros genéricos.

Esquema Rígido y Anti-Relacional 
-- ⚠️ Columnas fijas que violan la 1FN:
CREATE TABLE clientes_telefono_error (
    cliente_id  INT PRIMARY KEY,
    nombre      VARCHAR,
    telefono_1  VARCHAR,
    telefono_2  VARCHAR,
    telefono_3  VARCHAR -- ¿Y si tiene 4 teléfonos?
);
Relación 1:N Flexible y Atómica 
-- ✅ Tabla hija normalizada en 1FN/2FN:
CREATE TABLE cliente_telefonos (
    cliente_id INT REFERENCES clientes(cliente_id),
    telefono   VARCHAR NOT NULL,
    tipo       VARCHAR, -- 'Móvil', 'Oficina'
    PRIMARY KEY (cliente_id, telefono)
);
Anti-Patrón 2: Sobre-Normalización Prematura en Data Warehouses (OLAP)

La normalización hasta 3FN/BCNF es imperativa en sistemas transaccionales (OLTP) para asegurar la integridad de escrituras. Sin embargo, aplicarla ciegamente en almacenes de datos y analítica (OLAP) genera modelos con decenas de tablas pequeñas que obligan a realizar JOINs excesivos, penalizando el rendimiento de lectura.

💡 Solución Defensiva: En OLAP se emplean esquemas intencionalmente desnormalizados en Estrella (Star Schema) o Copo de Nieve (Snowflake), donde la redundancia controlada en tablas de dimensiones acelera drásticamente las consultas analíticas masivas.

Anti-Patrón 3: Guardar Listas de IDs en Cadenas de Texto Separadas por Comas

Almacenar valores como '101, 102, 105' en una columna de texto destruye la integridad referencial: el motor no puede verificar que los IDs existan, no se pueden crear claves foráneas y buscar un elemento requiere costosos escaneos de texto con LIKE '%102%' en lugar de búsquedas rápidas por índice.

5. Detalle:      detalle_factura(factura_id FK, producto_id FK, cantidad, precio_unitario,
                                 PRIMARY KEY(factura_id, producto_id))

Explicación: Se aislan las entidades maestras (Clientes, Vendedores, Productos) eliminando dependencias transitivas. El encabezado de la factura maneja la relación 1:N con clientes y vendedores, y el detalle resuelve la relación N:M con los productos en estricta 2FN y 3FN.

-- Solución Reto 2: Script DDL en DuckDB
CREATE TABLE clientes_reto (
    cliente_id INT PRIMARY KEY,
    cliente_nombre VARCHAR NOT NULL,
    ciudad_cliente VARCHAR NOT NULL
);

CREATE TABLE vendedores_reto (
    vendedor_id INT PRIMARY KEY,
    vendedor_nombre VARCHAR NOT NULL,
    depto_vendedor VARCHAR NOT NULL
);

CREATE TABLE productos_reto (
    producto_id INT PRIMARY KEY,
    producto_nombre VARCHAR NOT NULL,
    precio_base DECIMAL(12,2) NOT NULL
);

CREATE TABLE facturas_reto (
    factura_id INT PRIMARY KEY,
    fecha DATE NOT NULL,
    cliente_id INT REFERENCES clientes_reto(cliente_id),
    vendedor_id INT REFERENCES vendedores_reto(vendedor_id)
);

CREATE TABLE detalle_factura_reto (
    factura_id INT REFERENCES facturas_reto(factura_id),
    producto_id INT REFERENCES productos_reto(producto_id),
    cantidad INT CHECK (cantidad > 0),
    precio_unitario DECIMAL(12,2) NOT NULL,
    PRIMARY KEY (factura_id, producto_id)
);

Reto 3: Reconstrucción Completa de Facturas con JOIN Cuádruple en 3FN

Escribe una consulta de proyección que reconstruya la información completa de la factura original uniendo las 5 tablas normalizadas del Reto 2, calculando el subtotal por ítem (cantidad * precio_unitario) sin que exista pérdida de información ni tuplas espurias.

Ver Solución Comentada 
-- Solución Reto 3: Reconstrucción relacional exacta
SELECT 
    f.factura_id,
    f.fecha,
    c.cliente_nombre,
    c.ciudad_cliente,
    v.vendedor_nombre,
    p.producto_nombre,
    df.cantidad,
    df.precio_unitario,
    (df.cantidad * df.precio_unitario) AS subtotal
FROM facturas_reto f
JOIN clientes_reto c ON f.cliente_id = c.cliente_id
JOIN vendedores_reto v ON f.vendedor_id = v.vendedor_id
JOIN detalle_factura_reto df ON f.factura_id = df.factura_id
JOIN productos_reto p ON df.producto_id = p.producto_id
ORDER BY f.factura_id, p.producto_nombre;
