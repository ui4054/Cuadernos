01. Contexto Empresarial & El Problema en Producción

Desastres financieros provocados por tipos de datos inexactos y ausencia de restricciones

En sistemas de Cartera de Créditos, Banca y Cobranzas, una base de datos mal diseñada en su capa DDL transfiere la responsabilidad de integridad al código de la aplicación. Cuando fallan las validaciones del frontend o se ejecutan importaciones masivas (ETL), la base de datos almacena saldos negativos, tasas absurdas o pierde transacciones históricas completas.

El Error de Coma Flotante y Borrado Huérfano

Un desarrollador define el saldo del crédito como FLOAT en lugar de DECIMAL y omite la restricción CHECK en el saldo: 

-- DDL Deficiente en Producción:
CREATE TABLE creditos_inseguros (
    credito_id INT PRIMARY KEY,
    saldo FLOAT,             -- ⚠️ Error de coma flotante IEEE 754
    tasa_interes FLOAT       -- ⚠️ Permite valores negativos
);

⚠️ Consecuencia Contable: La suma de cuotas con FLOAT acumula descuadres de centavos ($0.0000000004$) imposibles de conciliar ante revisoría fiscal. Además, sin CHECK, un script con bug ingresa saldos negativos de $-\$5.000.000$ corrompiendo la cartera.

DDL Defensivo con Tipos Exactos e Integridad Referencial

Definición matemática estricta con DECIMAL(p,s), restricciones de dominio CHECK y control de borrado: 

-- DDL Defensivo de Misión Crítica:
CREATE TABLE creditos (
    credito_id INT PRIMARY KEY,
    saldo_actual DECIMAL(15,2) CHECK (saldo_actual >= 0),
    tasa_interes DECIMAL(5,2) CHECK (tasa_interes >= 0),
    estado VARCHAR CHECK (estado IN ('VIGENTE','MORA','PAGADO'))
);

✅ Resultado en Producción: Cualquier intento de ingresar saldos incoherentes es rechazado en microsegundos por el motor con un Constraint Error, garantizando consistencia absoluta independientemente de la aplicación cliente.

02. Cimiento Teórico Formal: Sublenguajes SQL & Cardinalidades

Taxonomía de comandos, integridad de entidad, referencial y resolución de relaciones N:M

El lenguaje SQL no es monolítico; está estructurado formalmente en **sublenguajes funcionales** según modifiquen los metadatos del catálogo, las tuplas en disco, o los permisos de acceso:

1. DDL (Data Definition Language)

Comandos que alteran la estructura del esquema relacional en el catálogo del sistema: CREATE, ALTER, DROP, TRUNCATE. Modifican metadatos y asignación de páginas.

2. DML (Data Manipulation Language)

Comandos que mutan el conjunto de tuplas persistidas dentro de las tablas: INSERT INTO, UPDATE, DELETE, MERGE. Operan bajo garantías transaccionales ACID.

3. DQL, DCL & TCL

DQL: SELECT (lectura y proyección).
DCL: GRANT, REVOKE (control de privilegios).
TCL: COMMIT, ROLLBACK, SAVEPOINT (transaccionalidad).

Cardinalidades Relacionales & Tablas Rompe-Relación (1:N vs N:M)

En el modelado relacional, las entidades se conectan mediante reglas de cardinalidad estrictas:

Relación 1:N (Uno a Muchos)

Un cliente puede solicitar múltiples créditos ($N$). En el modelo relacional físico, la clave primaria del lado 1 (cliente_id) migra como Clave Foránea (FK) hacia la tabla hija creditos.

Relación N:M (Muchos a Muchos) & Tabla Asociativa

Un crédito puede tener múltiples garantías (ej. Hipoteca + Fiador), y una garantía de alto valor puede amparar múltiples créditos. Las relaciones N:M no pueden implementarse directamente en bases relacionales sin violar la 1FN. Se requiere una Tabla Asociativa / Rompe-Relación (credito_garantias) con Clave Primaria Compuesta (credito_id, garantia_id).

03. Glosario de Palabras Clave

Sintaxis formal, comportamiento interno en el catálogo y soporte multi-motor

CREATE TABLE Sublenguaje DDL
SINTAXIS:
CREATE TABLE [IF NOT EXISTS] nombre_tabla (
    columna_1 tipo_dato [restricciones_columna],
    columna_2 tipo_dato [DEFAULT valor_defecto],
    [CONSTRAINT nombre_restriccion] PRIMARY KEY (columna_pk),
    [CONSTRAINT nombre_restriccion] FOREIGN KEY (columna_fk) REFERENCES tabla_padre(columna_padre)
);
EJEMPLO:
-- Creación de la entidad principal de clientes con restricciones defensivas
CREATE TABLE IF NOT EXISTS clientes_cartera (
    cliente_id INT PRIMARY KEY,
    nombre VARCHAR NOT NULL,
    doc_identidad VARCHAR UNIQUE NOT NULL,
    score_credito INT CHECK (score_credito BETWEEN 300 AND 950),
    cupo_aprobado DECIMAL(15,2) DEFAULT 5000000.00,
    ciudad VARCHAR DEFAULT 'Bogotá'
);
  • Mecánica Interna: Reserva entradas en el catálogo de metadatos del motor (ej. sqlite_master o pg_class) y asigna las estructuras de almacenamiento iniciales.
  • Cláusula IF NOT EXISTS: Previene excepciones fatales en scripts de automatización e infraestructura como código (IaC) si la tabla ya fue aprovisionada previamente.
  • Creación de Índices Implícitos: Al declarar PRIMARY KEY o UNIQUE, los motores relacionales generan automáticamente un índice B-Tree subyacente para acelerar búsquedas y garantizar unicidad.
ALTER TABLE Sublenguaje DDL
SINTAXIS:
ALTER TABLE nombre_tabla ADD COLUMN nombre_columna tipo_dato [restricciones];
ALTER TABLE nombre_tabla DROP COLUMN nombre_columna;
ALTER TABLE nombre_tabla ADD CONSTRAINT nombre_restriccion CHECK (...);
EJEMPLO:
-- Agrega una nueva columna para correo electrónico a clientes existentes
ALTER TABLE clientes_cartera ADD COLUMN email VARCHAR;
  • Evolución de Esquema sin Pérdida: Permite adaptar la base de datos a nuevos requerimientos del negocio sin tener que recrear la tabla ni migrar datos manualmente.
  • Bloqueo de Metadatos (Access Exclusive Lock): En motores tradicionales como PostgreSQL o SQL Server, ciertas operaciones ALTER TABLE adquieren bloqueos exclusivos sobre la tabla, por lo que deben ejecutarse en ventanas de mantenimiento controladas.
DROP TABLE vs. TRUNCATE TABLE Sublenguaje DDL
SINTAXIS:
TRUNCATE TABLE nombre_tabla;    -- Vacía los datos, preserva la estructura
DROP TABLE [IF EXISTS] nombre_tabla [CASCADE]; -- Destruye datos y estructura
EJEMPLO:
-- Vacía todas las tuplas de pagos preservando columnas y restricciones
TRUNCATE TABLE pagos_cartera;

-- Elimina definitivamente la tabla completa del diccionario del sistema
DROP TABLE IF EXISTS gestiones_cobranza;
  • TRUNCATE vs DELETE: TRUNCATE es una operación DDL de alta velocidad porque desasigna las páginas de datos en lugar de recorrer y registrar cada fila individual en el transaction log. Reinicia además los generadores de secuencia/autoincrementales.
  • Restricciones Foráneas: La mayoría de motores bloquean TRUNCATE si la tabla es referenciada por una Clave Foránea activa en otra tabla, incluso si la tabla hija está vacía.
  • DROP: Remueve la tabla, sus datos, disparadores (triggers) e índices asociados permanentemente.
PRIMARY KEY & FOREIGN KEY Restricciones de Integridad
SINTAXIS:
columna_id INT PRIMARY KEY
credito_id INT REFERENCES tabla_padre(columna_pk) [ON DELETE CASCADE | ON DELETE RESTRICT]
PRIMARY KEY (columna_a, columna_b) -- Clave Primaria Compuesta
EJEMPLO:
-- Tabla asociativa N:M con Clave Primaria Compuesta y Foráneas con borrado en cascada
CREATE TABLE credito_garantias (
    credito_id INT REFERENCES creditos(credito_id) ON DELETE CASCADE,
    garantia_id INT REFERENCES garantias(garantia_id) ON DELETE CASCADE,
    porcentaje_cobertura DECIMAL(5,2) CHECK (porcentaje_cobertura BETWEEN 0 AND 100),
    PRIMARY KEY (credito_id, garantia_id)
);
  • Integridad de Entidad (PK): Cada tupla debe ser unívocamente identificable. Una clave primaria impone implícitamente UNIQUE y NOT NULL.
  • Integridad Referencial (FK): Asegura que ningún registro hijo apunte a una clave inexistente en la tabla padre.
  • Acciones Referenciales: ON DELETE RESTRICT (por defecto en DuckDB y ANSI) bloquea el borrado de la tupla padre si existen registros dependientes; ON DELETE CASCADE propaga automáticamente el borrado eliminando a los hijos.
CHECK & DEFAULT Restricciones de Dominio
SINTAXIS:
columna tipo_dato CHECK (condicion_booleana)
columna tipo_dato DEFAULT valor_predeterminado
EJEMPLO:
-- Reglas de negocio embebidas en el motor:
CREATE TABLE creditos (
    credito_id INT PRIMARY KEY,
    monto_desembolsado DECIMAL(15,2) CHECK (monto_desembolsado > 0),
    saldo_actual DECIMAL(15,2) CHECK (saldo_actual >= 0),
    estado VARCHAR DEFAULT 'VIGENTE' CHECK (estado IN ('VIGENTE', 'MORA', 'PAGADO', 'CASTIGADO'))
);
  • Restricción CHECK: Se evalúa en cada operación de INSERT y UPDATE. La operación solo tiene éxito si la condición evalúa a TRUE o a UNKNOWN (¡ojo con los valores NULL en restricciones CHECK!).
  • Cláusula DEFAULT: Si una instrucción INSERT omite el atributo en su lista de proyección, el motor rellena automáticamente el campo con el valor o función especificada (ej. CURRENT_TIMESTAMP o 'VIGENTE').
INSERT INTO / UPDATE / DELETE Sublenguaje DML
SINTAXIS:
INSERT INTO tabla (col1, col2) VALUES (val1, val2);
UPDATE tabla SET col1 = nuevo_valor WHERE condicion;
DELETE FROM tabla WHERE condicion;
EJEMPLO:
-- 1. Insertar nueva tupla
INSERT INTO clientes_cartera (cliente_id, nombre, doc_identidad, score_credito)
VALUES (1, 'Tech Inversiones S.A.S.', '900123456-1', 820);

-- 2. Actualizar saldo aplicando penalización por mora del 5%
UPDATE creditos SET saldo_actual = saldo_actual * 1.05 WHERE estado = 'MORA';

-- 3. Borrado defensivo controlado
DELETE FROM clientes_cartera WHERE cliente_id = 5;
  • Mutación de Estado: Operan sobre las tuplas físicas existentes dentro de las páginas de datos.
  • El Peligro de Omitir el WHERE: Un UPDATE o DELETE sin WHERE mutará o borrará todas las filas de la tabla.
  • Verificación de Restricciones: Si cualquiera de las sentencias viola una restricción de integridad (PK duplicada, CHECK no satisfecho o violación de FK), el motor ejecuta un aborto transaccional automático (rollback) de la instrucción.

04. Laboratorio SQL & Desglose Línea a Línea

Anatomía completa de la definición DDL de la entidad financiera CREDITOS

Analicemos la instrucción DDL completa utilizada en producción para estructurar los desembolsos de cartera con integridad referencial y de dominio estricta: 

CREATE TABLE creditos (
    credito_id           INT PRIMARY KEY,
    cliente_id           INT NOT NULL REFERENCES clientes_cartera(cliente_id),
    monto_desembolsado   DECIMAL(15,2) CHECK (monto_desembolsado > 0),
    saldo_actual         DECIMAL(15,2) CHECK (saldo_actual >= 0),
    tasa_interes_anual   DECIMAL(5,2) CHECK (tasa_interes_anual >= 0),
    fecha_desembolso     DATE NOT NULL,
    estado               VARCHAR DEFAULT 'VIGENTE' 
                         CHECK (estado IN ('VIGENTE', 'MORA', 'PAGADO', 'CASTIGADO'))
);

Desglose Anatómico de Restricciones y Tipos Físicos

Línea SQL Cláusula / Restricción Mecánica Interna en el Motor de Base de Datos
L2 credito_id INT PRIMARY KEY Crea el identificador único entero del crédito. El motor genera automáticamente un índice B-Tree único no nulo para búsquedas directas por clave en $O(\log n)$.
L3 cliente_id INT NOT NULL REFERENCES ... Clave Foránea vinculada a clientes_cartera. Impone integridad referencial: no se puede crear un crédito para un cliente inexistente, y NOT NULL prohíbe créditos huérfanos.
L4 monto_desembolsado DECIMAL(15,2) CHECK ... Tipo numérico exacto de 15 dígitos con 2 decimales para evitar imprecisión de coma flotante. La regla CHECK (> 0) prohíbe desembolsos en cero o negativos.
L5 saldo_actual DECIMAL(15,2) CHECK (>= 0) Mantiene la deuda viva. La condición CHECK (>= 0) asegura que un crédito pagado llegue a cero, pero nunca a saldo negativo por abonos en exceso.
L6 tasa_interes_anual DECIMAL(5,2) CHECK (>= 0) Permite tasas hasta $999.99\%$. Prohíbe tasas de interés negativas que provocarían distorsión en la liquidación de intereses moratorios.
L7 fecha_desembolso DATE NOT NULL Tipo de fecha pura sin componente de hora (formato ISO-8601: YYYY-MM-DD). Obligatoria para cálculo de vencimientos.
L8 - L9 estado VARCHAR DEFAULT 'VIGENTE' CHECK (...) Si no se envía el estado al insertar, asume 'VIGENTE'. La restricción CHECK IN (...) implementa un tipo enumerado cerrado para la máquina de estados de cobranza.

07. Anti-Patrones y Consideraciones de Rendimiento

Errores graves en DDL y DML que destruyen la consistencia o bloquean tablas en producción

Anti-Patrón 1: Uso de FLOAT / REAL para Magnitudes Monetarias

Los tipos FLOAT y DOUBLE implementan la especificación de coma flotante binaria IEEE 754, la cual no puede representar fracciones decimales exactas en base 10 (ej. $0.1$ o $0.05$), acumulando discrepancias graves en sumatorias de cartera.

Riesgo Contable (Coma Flotante Inexacta) 
-- Genera errores de centavos:
CREATE TABLE pagos (
    pago_id INT PRIMARY KEY,
    monto FLOAT  -- ⚠️ Descuadre en conciliaciones
);
Estándar Financiero (Coma Fija Exacta) 
-- Precisión matemática decimal exacta:
CREATE TABLE pagos (
    pago_id INT PRIMARY KEY,
    monto DECIMAL(15,2) CHECK (monto > 0)
);
Anti-Patrón 2: DELETE Masivo sin WHERE en Tablas de Staging o Log

Ejecutar DELETE FROM tabla; para vaciar una tabla de staging con millones de filas bloquea los recursos, llena el transaction log (redo/undo) y puede agotar el espacio en disco.

DELETE Masivo (Bloqueo y Log Excesivo) 
-- Registra cada fila en el log individualmente:
DELETE FROM pagos_staging;
TRUNCATE (Desasignación Rápida) 
-- Libera páginas en microsegundos:
TRUNCATE TABLE pagos_staging;
Anti-Patrón 3: Intento de Eliminación de Registro Padre sin Orquestación Referencial

Intentar borrar un cliente que posee créditos activos arroja un Foreign Key Constraint Error. Para depurar o archivar entidades, se debe orquestar el borrado desde las tablas asociativas intermedias hacia las tablas hijas y finalmente la tabla padre.

Reto 1: DDL — Crear la Tabla `gestiones_cobranza` (Relación 1:N con Créditos)

Crea la tabla gestiones_cobranza para registrar contactos a deudores. Debe incluir: gestion_id como PK entera, credito_id como FK obligatoria a creditos, fecha_gestion con valor por defecto de marca de tiempo actual, tipo_contacto restringido con CHECK a: 'Llamada', 'Correo', 'Visita Campo', 'WhatsApp', compromiso_pago de tipo fecha y observaciones.

Ver Solución DDL Comentada 
-- Solución Reto 1:
CREATE TABLE IF NOT EXISTS gestiones_cobranza (
    gestion_id INT PRIMARY KEY,
    credito_id INT NOT NULL REFERENCES creditos(credito_id),
    fecha_gestion TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    tipo_contacto VARCHAR CHECK (tipo_contacto IN ('Llamada', 'Correo', 'Visita Campo', 'WhatsApp')),
    compromiso_pago DATE,
    observaciones VARCHAR
);

Explicación: Se aplica PRIMARY KEY, REFERENCES creditos(credito_id) para integridad referencial, DEFAULT CURRENT_TIMESTAMP para auditoría automática y CHECK IN (...) para restringir el canal.

Reto 2: DML — Insertar 2 Gestiones de Cobranza para Crédito en Mora

Escribe la instrucción INSERT INTO para registrar dos gestiones de cobro sobre el crédito 103 (el cual se encuentra en estado 'MORA'), una por llamada telefónica y otra por WhatsApp con compromisos de pago definidos.

Ver Solución DML Comentada 
-- Solución Reto 2:
INSERT INTO gestiones_cobranza (gestion_id, credito_id, fecha_gestion, tipo_contacto, compromiso_pago, observaciones) VALUES
(7001, 103, '2024-03-01 09:30:00', 'Llamada', '2024-03-15', 'Cliente solicita plazo adicional. Compromiso parcial.'),
(7002, 103, '2024-03-10 14:15:00', 'WhatsApp', '2024-03-20', 'Recordatorio vía WhatsApp. Confirma transferencia.');

Explicación: Se insertan dos tuplas verificando que el tipo_contacto coincida con los valores permitidos en el CHECK de la tabla creada en el Reto 1.

Reto 3: DML UPDATE — Bonificación de Score Crediticio a Clientes Cumplidos

Escribe una consulta de actualización con subconsulta para incrementar en +50 puntos el score_credito de todos los clientes que tengan al menos un crédito registrado en estado 'PAGADO', asegurando que no sobrepase el tope de 950 puntos.

Ver Solución DML UPDATE Comentada 
-- Solución Reto 3:
UPDATE clientes_cartera
SET score_credito = LEAST(score_credito + 50, 950)
WHERE cliente_id IN (
    SELECT DISTINCT cliente_id 
    FROM creditos 
    WHERE estado = 'PAGADO'
);

Explicación: La subconsulta identifica los cliente_id con créditos saldados, y la función LEAST(valor, 950) previene violar la restricción CHECK (score_credito <= 950).
