Conceptos centrales

Arquitectura en capas: ejemplo IMC

Fórmula del IMC

El Índice de Masa Corporal se calcula como:

\[ \text{IMC} = \frac{\text{Peso (kg)}}{\text{Altura (m)}^2} \]

Interpretación de los valores:

IMCClasificación
< 18.5Bajo peso
18.5 – 24.9Peso normal
25 – 29.9Sobrepeso
≥ 30Obesidad

Capa de datos (SQL Server)

Tabla Personas con columnas Id, Nombre, Edad, Peso, Altura:

```sql CREATE TABLE Personas ( Id INT PRIMARY KEY IDENTITY(1,1), Nombre NVARCHAR(100), Edad INT, Peso DECIMAL(5,2), Altura DECIMAL(4,2) ); ```

Consulta con cálculo de IMC y desviación estándar:

```sql SELECT Nombre, Peso, Altura, (Peso / (Altura * Altura)) AS IMC FROM Personas; SELECT STDEV(Peso / (Altura * Altura)) AS DesviacionEstandarIMC FROM Personas; ```

Capa lógica (C#)

Clase IMCCalculator que lee personas de la base de datos y calcula su IMC; clase Statistics para la desviación estándar:

```csharp persona.IMC = persona.Peso / (persona.Altura * persona.Altura); decimal media = imcs.Average(); decimal sumatoriaDesviaciones = imcs.Sum(imc => (imc - media) * (imc - media)); decimal desviacionEstandar = (decimal)Math.Sqrt((double)(sumatoriaDesviaciones / imcs.Count)); ```

Capa de presentación (C# consola)

El programa principal conecta a la base de datos, obtiene las personas con su IMC y muestra el resultado en consola.

Patrones de diseño

MVC y evolución del diseño

Modelo-Vista-Controlador y la transición de paradigmas de diseño.

Arquitectura MVC

Organiza la aplicación en tres componentes con responsabilidades separadas:

ComponenteResponsabilidad
ModeloLógica de aplicación y gestión de datos. Interactúa con la base de datos.
VistaInterfaz de usuario. Presenta datos sin lógica de negocio.
ControladorIntermediario entre modelo y vista. Procesa entradas del usuario.

Flujo: Controlador → Modelo (actualiza), Modelo → Vista (proporciona datos), Vista → Controlador (interacciones), Controlador → Vista (actualiza).

Principios SOLID

Buenas prácticas de diseño orientado a objetos

SRP, OCP, LSP, ISP y DIP para código mantenible y extensible.

PrincipioNombreDefinición resumida
SSingle ResponsibilityCada clase tiene una única razón para cambiar.
OOpen/ClosedAbiertas para extensión, cerradas para modificación.
LLiskov SubstitutionClases derivadas sustituyen a la base sin romper el programa.
IInterface SegregationInterfaces pequeñas y específicas, no generales grandes.
DDependency InversionDepender de abstracciones, no de implementaciones concretas.

Ejemplo SRP: una clase Usuario no debe enviar correos; eso corresponde a una clase separada ServicioEmail.

Ejemplo DIP: un Controlador depende de la interfaz IRepositorio, no de una implementación concreta de repositorio.

CQRS

Command Query Responsibility Segregation

Separación de operaciones de lectura y escritura.

Comandos (Commands)

Operaciones que modifican el estado del sistema (crear usuario, actualizar orden). Tienen efectos secundarios y lógica de negocio específica.

Consultas (Queries)

Operaciones que leen el estado sin modificarlo (obtener usuario por ID, listar órdenes). Optimizadas para rendimiento de lectura.

Separación de modelos

  • Modelos de comando: manejan lógica de negocio y actualizaciones de estado.
  • Modelos de consulta: proporcionan datos de forma eficiente para consultas específicas.

Beneficios: escalabilidad independiente de lectura/escritura, rendimiento optimizado, control de acceso diferenciado y flexibilidad para auditoría.
